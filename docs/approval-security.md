# 独立签名审批与信任边界

旧版填写 `approved: true` 的 JSON 只是一份自报记录，不能证明有人批准。新版执行器要求 Ed25519 签名：用户侧保存加密私钥，计算端只需要公钥。手写 JSON、改动已签收据、换用其它计划或混用阶段都应验签失败。

## 哪些技术措施实际生效

- `approve` 是独立交互命令，要求 stdin/stdout/stderr 为 TTY。不能用管道输入，也没有 `--yes`、密码参数或环境变量密钥接口。
- 签名私钥必须是带口令加密的 PKCS8 Ed25519 文件。口令通过隐藏的终端输入读取；无法保证隐藏输入时停止，避免退回明文回显。
- 收据签名覆盖计划指纹、审批阶段、明确动作、批准时间、操作者标识、决定说明及公钥指纹。计划绑定公钥文件的完整 SHA-256 和公钥标识。
- 求解/恢复审批还绑定那份已签“工程假设确认”文件的 SHA-256，并核验它的签名和先后时间。不能拿另一份确认收据替换。
- `assumptions`、`solve` 和 `resume` 是不同的签名动作。恢复计划需新的确认和恢复授权，原求解签名不能当成无限重试许可。
- 执行记录必须保存原始签名收据，而不是仅保存验签后解出的文本字段。

算法由 [cryptography 的 Ed25519 实现](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/) 提供；加密私钥使用其 [PKCS8 与 BestAvailableEncryption 接口](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/serialization/)。没有自制签名算法。该依赖延迟加载，离线规划不必加载私钥或密码学模块。

## “不能代签”的成立条件

**TTY 不是身份认证。** Agent 可以创建伪终端，因此 `isatty()` 只防止误用管道，不能证明按键来自人类。

密码学边界是：Agent 拿不到私钥的解密口令，也不能替换可信公钥或验签执行器。可信公钥必须由用户或宿主单独配置；从 Agent 自己提供的公钥开始信任，只能证明它签过字，不能证明用户批准。收据中的操作者姓名是被签名的声明，不是实名证书。

推荐把签名终端/私钥放在单独用户账户、另一台电脑或受控签名服务中；计算进程只读取受保护的可信公钥。人类核对计划指纹后签名，再将收据交给计算端。使用同一台电脑时，至少由用户管理私钥口令和可信根，不把它们交给 Agent，也不允许 Agent 修改审批器与执行器。

**若 Agent 与用户共享同一操作系统账户、拥有完整文件写入与任意代码执行权限，本项目不能给出绝对“技术上不可代签”的保证。** 它可以改执行器、替换公钥或监视不可信终端。此时需要先建立操作系统/宿主隔离边界，或使用用户在场确认的硬件/系统签名器。项目不会把 TTY 或一个可编辑配置文件描述为已经完成这种隔离。

## 用户操作

先在你控制的终端安装审批依赖，再调用 CLI 的 `approval-keygen` / `approve` 帮助。私钥存放在项目外，设置仅自己知道的口令；公开仓库、问题反馈和 Agent 聊天都不接收该口令。

```console
python -m pip install '.[approval]'
python -m comsol_workflow approval-keygen --help
python -m comsol_workflow approve --help
```

将公钥交给运行端并核对其指纹。在审阅完整案例、假设、资源预算和输出要求后，先签 `assumptions`，再针对同一计划签 `solve`。新计划或输入变更后重新确认。命令要求输入当前动作和计划摘要的精确确认短语，随后才解锁私钥。

不要让 Agent 创建一个它已知口令的“用户密钥”并替你签名。自动化测试使用临时测试密钥，始终标注为合成测试，不作为真实工程审批证据。第一次真实验证需要用户实际完成签名步骤。

## 本版本不提供的保证

不提供可信时间戳、证书实名认证、系统管理员攻击防护、硬件密钥托管或无人工参与的自动批准。签名能证明受信密钥批准过完整载荷；工程假设是否正确仍需要人审阅，操作系统信任根的配置也需要单独保障。
